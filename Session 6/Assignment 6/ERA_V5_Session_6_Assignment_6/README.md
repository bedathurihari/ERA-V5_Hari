# ERA V5 — Session 6, Assignment 6

I built this small, fully runnable training-data execution system to test reproducibility and auditability rather than model quality or scale.

## Run

```bash
python run_demo.py
python -m unittest discover -s tests -v
```

Python 3.10+; no external dependencies. The first command regenerates `submission_artifacts/` from scratch, including the complete log, evidence JSON/Markdown, manifests, ledgers, checkpoints, replay records and performance measurements.

## Design

- **Source and immutability:** Original illustrative documents in five lanes plus sealed evaluation/validation samples. Shards are saved as token arrays with content SHA-256, cleaning fingerprint, source/license, language metadata and token counts. Hash verification rejects tampering. The demonstrator re-creates frozen shards from source; an existing shard should never be edited in place in a real production run.
- **Tokenizer:** Explicitly versioned UTF-8 byte tokenizer with BOS=256, EOS=257, PAD=258; SHA-256 fingerprint stored in each shard manifest. Unicode Indic text is handled without installing a tokenizer.
- **Split firewall:** Only allowlisted train manifests enter the scheduler; evaluation and validation are blocked and recorded. This is a structural split firewall, not a semantic contamination/deduplication scanner.
- **Packing:** Fixed 12-token, isolated-document causal examples; tool traces use the same isolation but a distinct policy label. Masks exclude BOS and padding, position IDs reset at each sample; long documents are deterministically truncated with their spans recorded. No cross-document attention. This is intentionally conservative packing.
- **Curriculum:** Foundation and reasoning-focus stages, with protected minimum lane shares. Deterministic deficit allocation assigns 18 examples. An OPUS audit records accept/reject/defer/floor-override candidates; accepted suggestions are audited but **do not dynamically change the frozen run schedule**.
- **Training:** Actual 259×259 trainable bigram next-byte LM, online softmax SGD, token-level cross-entropy and token-to-document provenance. This is genuine optimization, not invented training metrics.
- **Recovery:** Checkpoint includes full model parameters, tokenizer hash, next consumption offset, and hash of the preceding consumption ledger. Deliberate in-process interruption before batch 3; model/offset restored and batch 3 consumed once. Subsequent offsets are contiguous.
- **Replay and fork:** Replay rebuilds batches from immutable shards and compiled schedule, comparing token span and batch SHA-256 for historical offsets 1–3. Fork loads the earlier checkpoint into a separate model instance and advances it independently.
- **Auditing:** Requirements are checked from actual generated objects. Logs, JSON/Markdown evidence, ledgers, performance counters and checkpoint files are generated by execution. Throughput is measured wall time on the host; numbers vary by machine.

## Scope and limitations

The unit of consumption is a deterministic **microbatch offset**; this example does not model distributed multi-worker execution, durable filesystem transaction protocols, optimizer state beyond online SGD, off-process crash injection, or a production-grade OPUS feedback loop. The deliberately triggered interruption is an in-process simulation, while restore and subsequent training use serialized checkpoints. The throughput metric includes pipeline setup, training and auditing. Reported mixture floors are stage target constraints; with only 18 selected samples, integer sampling can deviate from a floor and is reported separately. No external benchmarks are used for training.

The audit artifacts in `submission_artifacts/` are generated, not copied from this README. Run the script and inspect `evidence.json` and `run.log` for actual assertions.
