## Shape audit
The model is Embedding(32,24) -> Linear(24,24) + tanh -> Linear(24,32). For an example document with 9 input tokens:
- tokens: `(1,9)` — batch, sequence
- embeddings: `(1,9,24)` — batch, sequence, hidden
- hidden: `(1,9,24)` — batch, sequence, hidden
- logits: `(1,9,32)` — batch, sequence, vocabulary
- shifted logits: `(1,8,32)` — batch, loss positions, vocabulary
- targets: `(1,8)` — batch, loss positions
- reduced loss: `()` — scalar

## Finite-difference gradient check
I used fp64 and central differences with epsilon = `1e-5` on `ff.weight[0,0]`. In the original measured local run, backward returned `-0.0232079472`, finite differences returned `-0.0232079472`, absolute error `1.676e-11`. The notebook independently recomputes the check and asserts a tolerance of `1e-7`.

## Broken accumulation
The two documents contribute **8** and **3** predicted tokens respectively. The correct objective is `(sum of all token losses) / 11`; the intentionally broken objective is `0.5 * (mean of first document + mean of second document)`. The latter overweights the shorter document. Both models start from the same parameters and train for 80 SGD steps, evaluated with the correct token-weighted loss. In the original measured run: correct final loss `0.02872254`; broken final loss `0.03751455`. The plot is regenerated by the notebook.

## Gradient norms
I log the full-parameter L2 norm at **every one of 80 steps**, before calling `optimizer.step()`. Thus the first gradient norm is available before the first weight update and before any optimizer-driven decrease in loss. This is a temporal ordering observation, **not** evidence that the gradient norm predicts loss. The notebook prints the initial norm, initial loss and next-step loss.

## MFU and bottlenecks
The measured environment has PyTorch CPU, **no CUDA GPU**. An honest GPU MFU cannot be reported here, so **MFU = N/A**, not a manufactured percentage. The original CPU run had 2,168 parameters, 0.1224 s elapsed for two 80-step training trajectories, and a rough `6*N*tokens` proxy of about 187 MFLOP/s. This is *not* a hardware-calibrated MFU: the model is an embedding/MLP, not a transformer, and `6ND` is only a coarse proxy. Any comparison with 40% GPU MFU would be invalid. For actual CUDA measurement I would synchronize before/after timing, time forward+backward+optimizer over warm runs, record hardware SKU/precision/theoretical peak, profile kernels/memory/batch size, and compute model FLOPs divided by elapsed time and hardware peak. Small operations and launch/optimizer overhead would be likely contributors but are **hypotheses, not measured bottlenecks**.

## 0.1 in three formats
| Format | Sign / exponent / fraction | Full bits | Stored value |
|---|---|---|---|
| FP32 | `0 / 01111011 / 10011001100110011001101` | `00111101110011001100110011001101` | 0.100000001490 |
| BF16 | `0 / 01111011 / 1001101` | `0011110111001101` | 0.100097656250 |
| FP8 E4M3FN | `0 / 0011 / 101` | `00011101` | 0.101562500000 |

For this sort of training I would choose **BF16 on compatible GPU hardware**, while retaining FP32 for operations that need more precision. FP8 needs explicit scaling and convergence validation.

## Limitations
The run demonstrates a deterministic synthetic next-token task, not an industrial model. I did not claim GPU utilization or a predictive grad-norm event that the measurements did not show. Numerical results will vary slightly across platforms and PyTorch versions.
