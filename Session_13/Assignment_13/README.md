# Session 13 Assignment — 20M LLM, 50M Tokens, and Reversible Training

This assignment is my comparison of normal Transformer training against reversible training under the same token budget.

I wanted the comparison to answer a practical question: **if I spend extra computation to reconstruct activations during backward, how much GPU memory do I save, and can I use that memory to increase batch size?**

## Assignment requirements

I run three experiments:

1. **Baseline Transformer** — fixed batch size.
2. **Reversible Transformer** — the same fixed batch size.
3. **Reversible Transformer** — maximum batch size that fits on the GPU.

Every run targets **50,000,000 training tokens** and records:

- final training loss
- final validation loss
- average tokens/second
- CUDA peak allocated memory
- batch size
- tokens/step
- wall-clock time
- model parameter count

[`Session_13_Reversible_20M_LLM_50M_Tokens.ipynb`](./Session_13_Reversible_20M_LLM_50M_Tokens.ipynb)

## Reversible variant I used

I used **additive-coupling reversibility** rather than an approximate Euler inverse.

For one reversible block:

```text
y1 = x1 + F(x2)
y2 = x2 + G(y1)
```

The original activations can be reconstructed during backward:

```text
x2 = y2 - G(y1)
x1 = y1 - F(x2)
```

This is the main reason I chose this form: the inverse is algebraic. I do not have to assume that a single reverse Euler step recovers the original state.

`F` is the causal self-attention sublayer and `G` is the MLP sublayer.

I also disable dropout inside the reversible path, because stochastic recomputation would need RNG-state replay to reconstruct the same activations.

## Correctness check

Before training, the notebook runs a numerical sanity test that checks:

- maximum forward reconstruction error;
- input-gradient error against ordinary autograd;
- parameter-gradient error against ordinary autograd.

The expected result is an error close to floating-point roundoff. I treat this as a correctness gate before trusting the memory numbers.

## Batch-size policy

The fixed batch is set in the notebook configuration.

For the maximum-batch experiment, I do not guess a number. The notebook executes real forward and backward passes, increases the batch size until CUDA OOM, and then refines the boundary to find the largest batch that fits.

The learning-rate schedule is based on **tokens seen**, not steps. That avoids accidentally changing the schedule just because the batch size changes.

## Checkpointing

Colab sessions can disconnect, so each run periodically saves:

- model state;
- optimizer state;
- training step;
- tokens consumed;
- configuration.

If `latest.pt` exists, the same experiment resumes from it.

## What I expect to learn from the three runs

The fixed-batch comparison isolates the cost of reversibility. I expect the reversible run to use less depth-dependent activation memory but to lose some speed because `F` and `G` are recomputed during backward.

The maximum-batch run tests whether the saved memory is useful. If I can fit a larger batch, the GPU may recover some throughput by doing more work per step.

The most important point for me is that **reversibility is a compute-for-memory trade**. A lower peak-memory number by itself is not enough; I also need to report the throughput penalty and whether the larger usable batch changes the practical result.

## My takeaway

The assignment is not only about making a model reversible. The useful comparison is:

**normal activations → reversible reconstruction → spend the saved memory on a larger batch → measure the complete tradeoff.**

That is why I keep the model size and token budget controlled and report both memory and speed instead of reporting memory alone.
